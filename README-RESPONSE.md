# ErgoSOC-AU response (remediation) playbooks

These are a different category from the six enrichment playbooks in this repo. Enrichment
playbooks only read data and post a comment — nothing they do can hurt anything. These four
**write** to Entra ID or Defender for Endpoint: they revoke sessions, reset passwords, disable
accounts, mark identities compromised, isolate devices, and run antivirus scans. Deploy and grant
permissions for them deliberately, not as a drive-by extra.

| Playbook | Default name | Entity | What it does |
|---|---|---|---|
| Account: revoke + reset | `ErgoSOC-AU-Account-RevokeAndReset` | Account | Revokes all active sign-in sessions and/or forces a password reset with a random temporary password (never logged or shown anywhere) |
| Account: disable + confirm compromised | `ErgoSOC-AU-Account-DisableAndConfirmCompromised` | Account | Disables the Entra ID account and/or marks it compromised in Entra ID Protection |
| Device: isolate + scan | `ErgoSOC-AU-Device-IsolateAndScan` | Host | Fully isolates the device from the network and/or starts a quick Defender antivirus scan |
| Email: block + quarantine (assisted) | `ErgoSOC-AU-Email-BlockSenderAndQuarantine` | Mail message | **Does not call any write API.** Composes the exact PowerShell block command and Threat Explorer search values, and posts them to the incident — an analyst (or a separate automation) still has to run them. See "Why the email playbook doesn't automate the block" below. |

Generated by `build_response_account_contain.py`, `build_response_account_disable.py`,
`build_response_device_contain.py`, and `build_response_email_block.py`, sharing common WDL
helpers from `response_common.py`.

## The approval gate: none of these are wired to an automation rule

Every enrichment playbook in this repo is meant to be attached to an automation rule and fire
automatically — that's safe, because the worst a misfire can do is post a comment. These four are
not attached to anything, and this repo does not ship an automation rule for them. That's
deliberate: **an analyst manually clicking "Run playbook" on the incident (Sentinel Portal →
incident → Actions → Run playbook) is the approval step.** There's no Teams/email approval card
in front of them because building one honestly would mean an OAuth-delegated Teams or Outlook
connection — a real user's identity, not the managed identity everything else in this repo runs
as — which is a materially different trust model than the rest of the repo. A human deciding to
click "Run" on a reviewed incident is a simpler, equally real checkpoint that stays inside the
UAMI-only design.

If your team has decided a specific one of these should run with no human in the loop, that's a
legitimate choice — just make it deliberately, by attaching that one playbook to its own
automation rule (see the main [`README.md`](README.md#automation-rules--one-per-entity-type) for
the pattern). Don't do it by default.

## Every action reports success or failure — nothing is assumed to have worked

Each write call is checked against its expected success status code(s). The incident comment
always shows the actual outcome — `OK`, or `FAILED (HTTP <code>) - <api error message>` straight
from the API — never a blanket "done". If an action is turned off for that deployment, the comment
says `disabled by deployment setting`; if the entity's Entra object ID or Defender machine ID
couldn't be resolved, it says `skipped - could not resolve ...`. You can always tell, from the
comment alone, whether something actually happened.

## Permissions

These need materially more than the enrichment playbooks: write-scope Graph permissions, and for
the device playbook, a second grant against a completely different API. Get this right before
deploying — a UAMI with the wrong (or missing) permission just makes every action report
`FAILED`, which is safe but not useful.

### Account: revoke + reset (`azuredeploy-response-account-contain.json`)

Microsoft Graph application permission: **`User.ReadWrite.All`** (covers both
`revokeSignInSessions` and the `passwordProfile` reset).

```bash
GRAPH_APP_ID=00000003-0000-0000-c000-000000000000
GRAPH_SP_ID=$(az ad sp show --id "$GRAPH_APP_ID" --query id -o tsv)
GRAPH_ROLE_ID=$(az ad sp show --id "$GRAPH_APP_ID" \
  --query "appRoles[?value=='User.ReadWrite.All' && contains(allowedMemberTypes, 'Application')].id | [0]" \
  -o tsv)

az rest --method post \
  --uri "https://graph.microsoft.com/v1.0/servicePrincipals/$UAMI_PRINCIPAL_ID/appRoleAssignments" \
  --headers Content-Type=application/json \
  --body "{\"principalId\":\"$UAMI_PRINCIPAL_ID\",\"resourceId\":\"$GRAPH_SP_ID\",\"appRoleId\":\"$GRAPH_ROLE_ID\"}"
```

### Account: disable + confirm compromised (`azuredeploy-response-account-disable.json`)

Microsoft Graph application permissions: **`User.ReadWrite.All`** (disable) and
**`IdentityRiskyUser.ReadWrite.All`** (confirm compromised — requires Entra ID P2). Same pattern
as above, looped over both role names:

```bash
for GRAPH_ROLE in User.ReadWrite.All IdentityRiskyUser.ReadWrite.All; do
  GRAPH_ROLE_ID=$(az ad sp show --id "$GRAPH_APP_ID" \
    --query "appRoles[?value=='$GRAPH_ROLE' && contains(allowedMemberTypes, 'Application')].id | [0]" \
    -o tsv)
  az rest --method post \
    --uri "https://graph.microsoft.com/v1.0/servicePrincipals/$UAMI_PRINCIPAL_ID/appRoleAssignments" \
    --headers Content-Type=application/json \
    --body "{\"principalId\":\"$UAMI_PRINCIPAL_ID\",\"resourceId\":\"$GRAPH_SP_ID\",\"appRoleId\":\"$GRAPH_ROLE_ID\"}"
done
```

### Device: isolate + scan (`azuredeploy-response-device-contain.json`)

**Two separate grants, against two different resources.** Missing the second one is the most
common way this playbook silently fails.

1. Microsoft Graph application permission **`AdvancedQuery.Read.All`** (to resolve the Defender
   machine ID via `security/runHuntingQuery`) — same `az rest` pattern as above.
2. **WindowsDefenderATP** application permissions **`Machine.Isolate`** and **`Machine.Scan`** —
   this is a *different* enterprise application from Microsoft Graph (app ID
   `fc780465-2017-40d4-a0c5-307022471b92`), so it needs its own role-assignment call:

```bash
WDATP_APP_ID=fc780465-2017-40d4-a0c5-307022471b92
WDATP_SP_ID=$(az ad sp show --id "$WDATP_APP_ID" --query id -o tsv)

for WDATP_ROLE in Machine.Isolate Machine.Scan; do
  WDATP_ROLE_ID=$(az ad sp show --id "$WDATP_APP_ID" \
    --query "appRoles[?value=='$WDATP_ROLE' && contains(allowedMemberTypes, 'Application')].id | [0]" \
    -o tsv)
  az rest --method post \
    --uri "https://graph.microsoft.com/v1.0/servicePrincipals/$UAMI_PRINCIPAL_ID/appRoleAssignments" \
    --headers Content-Type=application/json \
    --body "{\"principalId\":\"$UAMI_PRINCIPAL_ID\",\"resourceId\":\"$WDATP_SP_ID\",\"appRoleId\":\"$WDATP_ROLE_ID\"}"
done
```

If `az ad sp show --id "$WDATP_APP_ID"` returns nothing, the WindowsDefenderATP service principal
hasn't been provisioned in your tenant yet — sign in to
[security.microsoft.com](https://security.microsoft.com) once as a Global/Security Administrator
first, which provisions it automatically.

### Email: block + quarantine (`azuredeploy-response-email-block.json`)

**No Graph write permission needed.** This playbook makes no write API call at all (see below) —
`Microsoft Sentinel Responder` on the resource group is the only grant required, same as an
enrichment playbook.

Allow several minutes for new role assignments to propagate before testing any of these.

## Why the email playbook doesn't automate the block

Writing to the Microsoft 365 Tenant Allow/Block List only has one reliably-documented path:
Exchange Online PowerShell's `New-TenantAllowBlockListItems` / `Set-TenantAllowBlockListItems`
cmdlets. There is a `security/tenantAllowBlockLists` surface in the Microsoft Graph **beta** API,
but multiple independent reports (including Microsoft's own Q&A forum) say the write path isn't
reliably exposed there — it's effectively EXO-PowerShell-only in practice. Shipping a guessed
Graph POST for a security containment action would be worse than not automating it: it would
silently do nothing while the incident comment claimed success.

So this playbook composes the exact `New-TenantAllowBlockListItems` command(s) for the sender
and/or domain, plus the message's Network message ID, Subject, Sender, and Recipient, and posts
them to the incident comment for an analyst to run — or for a separate automation to pick up, if
your environment already has an Automation Account or Function App doing app-only EXO PowerShell
(via the `Exchange.ManageAsApp` API permission and certificate auth). That's a meaningfully bigger
piece of infrastructure than the plain UAMI-HTTP pattern the rest of this repo uses, which is why
it isn't built into the Logic App itself.

## Deploy

Same shape as every other playbook in this repo — one UAMI, one `az deployment group create`:

```bash
az deployment group create \
  --name sentinel-response-account-contain \
  --resource-group "$SENTINEL_RG" \
  --template-file azuredeploy-response-account-contain.json \
  --parameters UserAssignedManagedIdentityResourceId="$UAMI_ID"
```

Repeat with the other three template files and unique deployment names. Each has its own
per-action bool parameters (e.g. `RevokeSessions`, `ResetPassword`) if you want to deploy with
only one half of a pair turned on.

After deploying, authorise the Microsoft Sentinel API connection for each (same manual
one-time step every playbook in this repo needs), then **do not** attach any of them to an
automation rule unless that's a deliberate decision — see above.
