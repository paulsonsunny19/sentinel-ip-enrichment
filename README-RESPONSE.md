# ErgoSOC-AU response (remediation) playbooks

These are a different category from the six enrichment playbooks in this repo. Enrichment
playbooks only read data and post a comment — nothing they do can hurt anything. These seven
**write** to Entra ID, Defender for Endpoint, or (optionally) Exchange Online: they revoke
sessions, reset passwords, disable accounts, mark identities compromised, revoke OAuth app
consent, isolate devices, run antivirus scans, restrict app execution, and block IP/URL/file-hash
indicators tenant-wide. Deploy and grant permissions for them deliberately, not as a drive-by
extra.

| Playbook | Default name | Entity | What it does |
|---|---|---|---|
| Account: revoke + reset | `ErgoSOC-AU-Account-RevokeAndReset` | Account | Revokes all active sign-in sessions and/or forces a password reset with a random temporary password (never logged or shown anywhere) |
| Account: disable + confirm compromised | `ErgoSOC-AU-Account-DisableAndConfirmCompromised` | Account | Disables the Entra ID account and/or marks it compromised in Entra ID Protection |
| Account: revoke app consent | `ErgoSOC-AU-Account-RevokeAppConsent` | Account | Lists and revokes every delegated OAuth2 permission grant the user has consented to |
| Device: isolate, scan, restrict | `ErgoSOC-AU-Device-IsolateAndScan` | Host | Fully isolates the device, starts a quick Defender antivirus scan, and/or restricts app execution to Microsoft-signed binaries |
| Email: block + quarantine | `ErgoSOC-AU-Email-BlockSenderAndQuarantine` | Mail message | Composes the exact PowerShell block command and Threat Explorer search values. **Assisted by default** (no write call); optionally auto-executes via an Automation Account if you set it up. See below. |
| FileHash: block indicator | `ErgoSOC-AU-FileHash-BlockIndicator` | FileHash | Submits a tenant-wide block indicator to Defender for Endpoint via Microsoft Graph |
| IP/URL: block indicator | `ErgoSOC-AU-Indicator-Block` | IP, URL | Submits a tenant-wide block indicator to Defender for Endpoint for each IP and/or URL entity |

Generated by `build_response_account_contain.py`, `build_response_account_disable.py`,
`build_response_account_revoke_consent.py`, `build_response_device_contain.py`,
`build_response_email_block.py`, `build_response_filehash_block.py`, and
`build_response_indicator_block.py`, sharing common WDL helpers from `response_common.py`.

## The approval gate: none of these are wired to an automation rule

Every enrichment playbook in this repo is meant to be attached to an automation rule and fire
automatically — that's safe, because the worst a misfire can do is post a comment. These seven are
not attached to anything, and this repo does not ship an automation rule for them. That's
deliberate: **an analyst manually clicking "Run playbook" on the incident (Sentinel Portal →
incident → Actions → Run playbook) is the approval step.** There's no Teams/email approval card
in front of them because building one honestly would mean an OAuth-delegated Teams or Outlook
connection — a real user's identity, not the managed identity everything else in this repo runs
as — which is a materially different trust model than the rest of the repo. A human deciding to
click "Run" on a reviewed incident is a simpler, equally real checkpoint that stays inside the
UAMI-only design.

If your team has decided a specific one of these should run with no human in the loop, that's a
legitimate choice — just make it deliberately, by attaching that one playbook to its own
automation rule (see the main [`README.md`](README.md#automation-rules--one-per-entity-type) for
the pattern). Don't do it by default.

## Every action reports success or failure — nothing is assumed to have worked

Each write call is checked against its expected success status code(s). The incident comment
always shows the actual outcome — `OK`, or `FAILED (HTTP <code>) - <api error message>` straight
from the API — never a blanket "done". If an action is turned off for that deployment, the comment
says `disabled by deployment setting`; if the entity's Entra object ID or Defender machine ID
couldn't be resolved, it says `skipped - could not resolve ...`. You can always tell, from the
comment alone, whether something actually happened.

## Permissions

These need materially more than the enrichment playbooks: write-scope Graph permissions, and for
some, a second grant against a completely different API. Get this right before deploying — a UAMI
with the wrong (or missing) permission just makes every action report `FAILED`, which is safe but
not useful.

The `az rest` role-assignment pattern below is the same for every Graph permission in this
section — only the app ID (Graph vs WindowsDefenderATP) and role name(s) change:

```bash
GRAPH_APP_ID=00000003-0000-0000-c000-000000000000
GRAPH_SP_ID=$(az ad sp show --id "$GRAPH_APP_ID" --query id -o tsv)

for GRAPH_ROLE in <role names go here>; do
  GRAPH_ROLE_ID=$(az ad sp show --id "$GRAPH_APP_ID" \
    --query "appRoles[?value=='$GRAPH_ROLE' && contains(allowedMemberTypes, 'Application')].id | [0]" \
    -o tsv)
  az rest --method post \
    --uri "https://graph.microsoft.com/v1.0/servicePrincipals/$UAMI_PRINCIPAL_ID/appRoleAssignments" \
    --headers Content-Type=application/json \
    --body "{\"principalId\":\"$UAMI_PRINCIPAL_ID\",\"resourceId\":\"$GRAPH_SP_ID\",\"appRoleId\":\"$GRAPH_ROLE_ID\"}"
done
```

| Playbook | Permission(s) needed | Resource |
|---|---|---|
| Account: revoke + reset | `User.ReadWrite.All` | Microsoft Graph |
| Account: disable + confirm compromised | `User.ReadWrite.All`, `IdentityRiskyUser.ReadWrite.All` (requires Entra ID P2) | Microsoft Graph |
| Account: revoke app consent | `DelegatedPermissionGrant.ReadWrite.All` | Microsoft Graph |
| Device: isolate, scan, restrict | `ThreatHunting.Read.All` (machine ID lookup) | Microsoft Graph |
| Device: isolate, scan, restrict | `Machine.Isolate`, `Machine.Scan`, `Machine.RestrictExecution` | **WindowsDefenderATP** (a *different* enterprise app, ID `fc780465-2017-40d4-a0c5-307022471b92`) |
| Email: block + quarantine (assisted mode) | none | — no write call made |
| Email: block + quarantine (auto-execute mode) — Logic App's own UAMI | `Automation Job Operator` Azure RBAC role, scoped to the Automation Account | Azure Resource Manager, not Graph |
| Email: block + quarantine (auto-execute mode) — Automation Account's dedicated identity | `Tenant AllowBlockList Manager` role group | **Exchange Online's own RBAC**, not Azure RBAC or a Graph app role |
| FileHash: block indicator | `Ti.ReadWrite.All` | **WindowsDefenderATP** (not Microsoft Graph — see note below) |
| IP/URL: block indicator | `Ti.ReadWrite.All` | **WindowsDefenderATP** (not Microsoft Graph — see note below) |

For the WindowsDefenderATP grant, swap `GRAPH_APP_ID` for `WDATP_APP_ID=fc780465-2017-40d4-a0c5-307022471b92`
in the loop above. If `az ad sp show --id "$WDATP_APP_ID"` returns nothing, that service principal
hasn't been provisioned in your tenant yet — sign in to
[security.microsoft.com](https://security.microsoft.com) once as a Global/Security Administrator
first, which provisions it automatically.

The Automation Job Operator grant (for email auto-execute) is ordinary Azure RBAC, not a Graph
app-role assignment:

```bash
az role assignment create \
  --assignee-object-id "$UAMI_PRINCIPAL_ID" \
  --assignee-principal-type ServicePrincipal \
  --role "Automation Job Operator" \
  --scope "$AUTOMATION_ACCOUNT_RESOURCE_ID"
```

Allow several minutes for new role assignments to propagate before testing any of these.

### Why FileHash/IP/URL block use WindowsDefenderATP, not Microsoft Graph

This took three attempts to get right, worth documenting so nobody rediscovers the same dead ends.
The FileHash and IP/URL block-indicator playbooks originally called Microsoft Graph's
`security/tiIndicators`. In order:

1. `v1.0/security/tiIndicators` — 400, "Resource not found for the segment 'tiIndicators'". That
   resource was never promoted to v1.0, only `beta`.
2. `beta/security/tiIndicators` — 400, "The ISG Graph API has been deprecated as of April 2026."
   Microsoft's own deprecation notice for `tiIndicator` points at Sentinel's native
   `Microsoft.SecurityInsights/threatIntelligenceIndicators` ARM resource — but that one feeds
   Sentinel's own analytics-rule *matching/alerting*, not enforcement; submitting an indicator
   there doesn't block anything on a device, a real capability gap versus what these playbooks are
   for.
3. **Defender for Endpoint's own indicators API** (`POST https://api.security.microsoft.com/api/indicators`)
   — a separate product surface from the deprecated Graph "ISG" layer, unaffected by that
   deprecation, and it's what actually enforces the block on managed devices. This is what both
   playbooks use now. It reuses the same `Ti.ReadWrite.All` **WindowsDefenderATP** application
   permission family as the device-containment playbook's `Machine.Isolate`/`Machine.Scan`/
   `Machine.RestrictExecution` — same enterprise app (ID `fc780465-2017-40d4-a0c5-307022471b92`),
   same `az rest` grant pattern, different role name.

One side effect: this API's `indicatorType: "IpAddress"` covers both IPv4 and IPv6 in one
submission, so the IP/URL playbook no longer needs separate v4/v6 branching — one HTTP call per IP
entity.

If you'd previously granted `ThreatIndicators.ReadWrite.OwnedBy` on Microsoft Graph for these two
playbooks per earlier guidance, it's now unused and safe to remove — replace it with
`Ti.ReadWrite.All` on WindowsDefenderATP per the table above.

## Why the email playbook is assisted by default

Writing to the Microsoft 365 Tenant Allow/Block List only has one reliably-documented path:
Exchange Online PowerShell's `New-TenantAllowBlockListItems` / `Set-TenantAllowBlockListItems`
cmdlets. There is a `security/tenantAllowBlockLists` surface in the Microsoft Graph **beta** API,
but multiple independent reports (including Microsoft's own Q&A forum) say the write path isn't
reliably exposed there — it's effectively EXO-PowerShell-only in practice. Shipping a guessed
Graph POST for a security containment action would be worse than not automating it: it would
silently do nothing while the incident comment claimed success.

So by default, `ErgoSOC-AU-Email-BlockSenderAndQuarantine` composes the exact
`New-TenantAllowBlockListItems` command(s) for the sender and/or domain, plus the message's
Network message ID, Subject, Sender, and Recipient, and posts them to the incident comment for an
analyst to run.

### Optional: auto-execute the block via an Automation Account

If you want this actually automated, this repo includes the infrastructure for it. **Two separate
identities are involved, deliberately** — the Logic App's own UAMI (shared with the rest of this
repo) only ever gets permission to *start a job*; a second, dedicated UAMI is what the runbook
authenticates to Exchange Online as, so that one identity's tenant-wide mail-write access stays
isolated from everything else this repo's playbooks can touch.

1. **Create the dedicated identity** for the Automation Account (not the shared one):
   ```bash
   EXO_UAMI_ID=$(az identity create \
     --resource-group "$SENTINEL_RG" \
     --name ErgoSOC-AU-EXO-Automation-Identity \
     --query id -o tsv)
   ```

2. **Deploy the Automation Account, assigned that dedicated identity.**
   ```bash
   az deployment group create \
     --name sentinel-response-automation \
     --resource-group "$SENTINEL_RG" \
     --template-file azuredeploy-automation-account-response.json \
     --parameters UserAssignedManagedIdentityResourceId="$EXO_UAMI_ID"
   ```
   This creates the Automation Account (with that identity attached), imports the
   `ExchangeOnlineManagement` PowerShell module, and creates an empty runbook resource. Grab the
   identity's client ID from the deployment output — you'll need it in steps 3 and 5:
   ```bash
   EXO_CLIENT_ID=$(az deployment group show \
     --resource-group "$SENTINEL_RG" --name sentinel-response-automation \
     --query properties.outputs.managedIdentityClientId.value -o tsv)
   ```
   ARM can't reliably inline multi-line PowerShell as JSON, so the runbook's actual content is
   published separately:
   ```bash
   az automation runbook replace-content \
     --resource-group "$SENTINEL_RG" \
     --automation-account-name ErgoSOC-AU-ResponseAutomation \
     --name Set-ErgoSOC-TenantBlockListItem \
     --content @runbooks/Set-ErgoSOC-TenantBlockListItem.ps1
   az automation runbook publish \
     --resource-group "$SENTINEL_RG" \
     --automation-account-name ErgoSOC-AU-ResponseAutomation \
     --name Set-ErgoSOC-TenantBlockListItem
   ```

3. **Register the dedicated identity in Exchange Online and grant it a scoped role.** No
   certificate, no app registration — the runbook connects as this identity directly
   (`Connect-ExchangeOnline -ManagedIdentity`). Exchange Online has its own separate RBAC system
   from Azure/Graph, so this is a one-time step run interactively by a Global or Exchange admin.
   Give it a role scoped to just the allow/block list — do not grant it Organization Management:
   ```powershell
   Connect-ExchangeOnline
   New-ServicePrincipal -AppId $EXO_CLIENT_ID -ObjectId <the dedicated identity's principal ID> `
     -DisplayName "ErgoSOC-AU-EXO-Automation-Identity"
   New-RoleGroup -Name "ErgoSOC-AU-TABL-Managers" `
     -Roles "Tenant AllowBlockList Manager" -Members "ErgoSOC-AU-EXO-Automation-Identity"
   ```
   (Get the identity's principal/object ID with
   `az identity show --ids "$EXO_UAMI_ID" --query principalId -o tsv`.)

4. **Grant the Logic App's (shared) UAMI permission to start jobs on the Automation Account** (see
   the Automation Job Operator command earlier in this file).

5. **Redeploy `azuredeploy-response-email-block.json`** with `AutoExecuteBlock=true` and the
   `AutomationAccountResourceId`/`ExoManagedIdentityClientId` (= `$EXO_CLIENT_ID`)/`ExoOrganization`
   parameters filled in. Leave `AutoExecuteBlock=false` (the default) if you'd rather keep it
   assisted-only — nothing changes about the playbook's existing behavior until you explicitly turn
   it on.

Once enabled, the playbook submits the block as an Automation job (fire-and-forget — the Job API
is asynchronous) and reports the job ID in the incident comment; check the Automation Account's
Jobs blade for the actual completion status.

## Deploy

Same shape as every other playbook in this repo — one UAMI, one `az deployment group create`:

```bash
az deployment group create \
  --name sentinel-response-account-contain \
  --resource-group "$SENTINEL_RG" \
  --template-file azuredeploy-response-account-contain.json \
  --parameters UserAssignedManagedIdentityResourceId="$UAMI_ID"
```

Repeat with the other template files and unique deployment names. Each has its own per-action bool
parameters (e.g. `RevokeSessions`, `ResetPassword`, `BlockIP`, `BlockUrl`) if you want to deploy
with only some actions turned on.

### Deploy all seven in one go

`azuredeploy-response-all.json` deploys all seven response playbooks as one ARM deployment (each
as a nested deployment, still with its own dedicated Sentinel connection) — one
`az deployment group create` call instead of seven, generated by `build_response_master_template.py`
(same nested-deployment pattern as the six enrichment playbooks' `azuredeploy-all.json`):

```bash
az deployment group create \
  --name sentinel-response-all \
  --resource-group "$SENTINEL_RG" \
  --template-file azuredeploy-response-all.json \
  --parameters UserAssignedManagedIdentityResourceId="$UAMI_ID"
```

`PlaybookName` is exposed per playbook since each Logic App needs a distinct resource name
(`AccountContainPlaybookName`, `AccountDisablePlaybookName`, `AccountRevokeConsentPlaybookName`,
`DeviceContainPlaybookName`, `EmailBlockPlaybookName`, `FileHashBlockPlaybookName`,
`IndicatorBlockPlaybookName`), each still defaulting to that playbook's own original name.
`Action` and `IndicatorExpirationDays` are merged into one shared parameter each (both the
FileHash and IP/URL block-indicator playbooks have them, same meaning). Everything else keeps its
own per-playbook name — 26 master parameters in total.

The safety model is identical either way: **none of the seven are wired to an automation rule by
this template either.** Deploying the bundle doesn't change that — see above.

### Deploy six together, keep Email separate

If you'd rather set up the Email block playbook's Automation Account / dedicated identity path on
its own schedule, `azuredeploy-response-without-email.json` bundles the other six (same pattern,
same generator — `build_response_master_template.py` writes both files):

```bash
az deployment group create \
  --name sentinel-response-without-email \
  --resource-group "$SENTINEL_RG" \
  --template-file azuredeploy-response-without-email.json \
  --parameters UserAssignedManagedIdentityResourceId="$UAMI_ID"

az deployment group create \
  --name sentinel-response-email-block \
  --resource-group "$SENTINEL_RG" \
  --template-file azuredeploy-response-email-block.json \
  --parameters UserAssignedManagedIdentityResourceId="$UAMI_ID"
```

18 master parameters (no `EmailBlockPlaybookName`, `AutoExecuteBlock`, or any `Exo*`/
`AutomationAccountResourceId`/`RunbookName` parameter — those only exist on the email playbook's
own template). Same safety model as every other option here.

After deploying (either way), authorise the Microsoft Sentinel API connection for each (same
manual one-time step every playbook in this repo needs), then **do not** attach any of them to an
automation rule unless that's a deliberate decision — see above.
